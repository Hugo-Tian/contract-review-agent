# 明约：面向普通消费者的合同理解与承诺核验智能体

参赛方向建议：办公 / 文档处理 / 流程自动化。当前为参赛准备版，尚未报名，未获官方认证。

## 用户与问题
中国大陆培训、求职辅导合同的学员和付款家长，常常无法判断销售口头承诺是否写入合同、开通账号是否算完成服务、提前退出会如何扣费。明约把合同原话、通俗解释和下一步询问放在一起，帮助用户核对后决策。

## 创新与完整任务
接收PDF、DOCX、图片或文本，必要时执行本机OCR。用户核对正文与版本后，系统按明确规则执行合同分析、引用校验、可选销售承诺对照、按目标检索法规选编，并展示各步骤状态。退款计算保留人工确认门槛，不从不完整信息猜测金额。报告和任务记录可手动保存，版本差异可独立比较。

区别于直接向模型提问：后端以编号证据回填原文，拒绝不存在的引用；计算由Decimal执行；人工确认发送与计算输入；辅助工具失败不抹掉已完成报告。引用存在不保证分析语义正确。

## 技术方案
Vue + FastAPI；DeepSeek兼容API；本机RapidOCR；SQLite临时及用户主动保存历史。
流程：导入/OCR → 用户核对 → 确认发送 → 分析与证据核验 → 有销售文字则对照 → 按目标检索法规 → 人工处理退款及协商。
/api/workflow 为 openJiuwen SDK 显式工作流入口，执行轨迹是系统操作摘要，不是模型隐藏思考过程。没有无边界自主规划，也没有自动发送消息或替用户决定法律结论。

已集成 openJiuwen Python SDK 0.1.18：Workflow/WorkflowCard 定义有向图，五个 WorkflowComponent 节点由 Workflow.invoke 与独立会话调度。DeepSeek仍通过已有兼容API适配器调用，以保留结构化输出和证据核验。没有使用JiuwenSwarm，也没有声称SDK会自动给出法律判断。

## 可靠性与边界
模型输出受结构及证据校验约束；版本不一致拒绝运行；无同意不发送；演示模式不调用模型。法规仅为四部法规的46条选编，不是完整RAG或实时法律数据库。单用户本机运行，无公网多用户能力。实际模型风险识别准确率尚未建立，不能把软件单元测试通过率当准确率。
