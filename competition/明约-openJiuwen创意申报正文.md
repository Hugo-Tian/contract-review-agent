# 明约——基于 openJiuwen 的合同理解与销售承诺核验智能体

## 参赛方向
办公：文档处理、流程自动化与知识辅助应用。

## 项目简介
明约是一款面向普通消费者的合同理解与销售承诺核验智能体，首期聚焦中国大陆培训、求职辅导合同。针对合同难读、销售说法与书面条款难核对、退出扣费难理解等问题，项目基于 openJiuwen SDK 编排合同核验流程，结合 DeepSeek、本机 OCR、原文引用校验和确定性计算，将合同转化为通俗解释、承诺对照结果、退款情景试算及可直接使用的询问草稿。用户能够看到问题对应的原文和任务执行记录，并在发送模型、核对金额等关键环节保留确认权。目前已完成可运行原型，通过46项自动化测试，并完成虚构合同的真实模型端到端验证。

## 一、目标用户与需求痛点
项目主要服务培训学员、求职辅导服务购买者及付款家长。用户往往在签约前收到“保证就业”“不满意全额退款”等销售说法，却难以确认这些承诺是否真正写入合同；付款后，又可能面对“账号开通即视为交付”“按分项标价扣费”等难以理解的约定。

现有阅读方式要求用户自行找条款、比对聊天内容、计算扣费，再组织询问。明约把这些分散步骤组织成可追溯的任务流程，帮助用户回答三个具体问题：机构到底答应提供什么、提前退出可能如何扣费、还有哪些内容需要书面确认。

## 二、应用场景与使用流程
### 1. 签约前：把销售说法放回合同核对
用户导入 PDF、DOCX、图片或粘贴文本；扫描件和图片可在本机进行 OCR。核对提取结果后，用户补充阅读目标和销售说法，并确认发送范围。系统生成通俗解释、引用原文、逐条承诺对照和询问草稿，帮助用户在付款前问清服务内容、交付标准、附件及退出安排。

### 2. 付款后：理解退出成本
用户查看退款相关条款，手动确认实付金额、已使用服务、价格与扣费依据，再使用退款工具比较不同扣费情景。系统展示计算过程，不猜测缺失价格，也不把情景试算当作最终法律可退金额。

### 3. 协商中：比较修改并保留阅读记录
用户可比较修订前后或另一份合同的文字差异，检查口头补充是否进入书面约定；也可主动保存报告到本机历史，后续恢复、查看或导出。

## 三、基于 openJiuwen 的技术方案
项目使用 openJiuwen Python SDK 0.1.18，以 Workflow 和 WorkflowCard 定义工作流，以五个 WorkflowComponent 节点实现任务，通过独立会话和 Workflow.invoke 执行：

正文确认 → 合同分析与引用核验 → 销售承诺核验 → 法规参考检索 → 报告汇总与待确认事项。

节点根据用户目标、输入材料及运行模式处理任务：没有销售说法时跳过承诺对照；演示模式不调用模型；退款目标优先检索退款、违约金相关选编条文。执行结束后展示各步骤的完成、跳过、失败和待确认状态。主分析失败会阻断后续处理，承诺或法规辅助步骤失败则保留已完成报告，并提示重试。

DeepSeek通过兼容API适配器承担文本分析，后端继续执行输出结构检查和原文引用核验。前端采用Vue，后端采用FastAPI，OCR在本机运行，SQLite用于临时数据与用户主动保存的历史。合同正文和报告保留在请求内业务状态中，SDK节点输入输出只传递执行状态，减少敏感内容进入框架追踪的机会。

当前采用可控的规则工作流，不依赖无边界自主规划；使用的是openJiuwen SDK，尚未接入JiuwenSwarm。OCR、退款试算、版本比较及历史管理作为配套工具供用户按需使用。

## 四、项目创新与实用价值
### 1. 让解释有可核对的出处
模型通过编号选择证据片段，后端回填对应原话与位置，并拒绝不存在的引用。用户可以从报告直接定位合同原文，核对解释所依据的内容。该机制保证引用出处存在，但不替代对推理正确性的人工复核。

### 2. 把合同分析与销售承诺对照结合起来
项目同时关注书面约定和用户提供的销售说法，呈现“合同有写”“说法不一致”“合同没找到”等结果，并给出具体追问，帮助用户发现交易沟通中容易忽略的差异。

### 3. 面向非专业用户组织结果
报告围绕“这条在说什么”“对你有什么影响”“可以直接怎样问”展开，将较难理解的条款转化为日常语言，并提供可编辑的协商草稿。用户保留最终判断和发送决定。

### 4. 为不同任务选择可核验的方法
文本理解交给模型，金额计算使用Decimal，法规参考来自本机官方条文选编，正文修订保留版本信息。通过明确分工，提高流程的可解释性和可检查性。

## 五、当前成果与验证
目前已完成合同导入、本机OCR、正文修订、通俗报告、原文定位、销售承诺对照、退款情景试算、法规选编检索、版本比较和本机历史保存。

SDK环境下46项自动化测试全部通过，覆盖文件解析、OCR、引用校验、金额计算、版本约束、历史恢复、SDK节点调度、用户确认门槛及辅助失败处理；前端类型检查和生产构建通过。

在虚构求职辅导合同的真实DeepSeek验证中，系统完成五节点工作流，并将销售“保证正式录用”与合同“不保证正式录用”识别为说法不一致，展示对应原文与询问建议。该验证证明流程能够运行，不代表已建立法律正确性或模型准确率指标。

## 六、后续开发计划
下一阶段将围绕真实使用效果完善产品：建立20—30份公开或模拟合同的人工标注集，分别评估文字提取、风险识别及引用支持性；邀请目标用户试用，检验报告是否容易理解、问题是否便于询问；进一步优化复杂表格、长合同处理与任务进度展示。

首期继续聚焦培训和求职辅导场景，待获得验证数据后，再评估向其他消费服务合同扩展，逐步形成可复用的合同理解工作流。

## 七、能力边界与数据保护
当前版本面向中国大陆合同语境，提供辅助阅读与沟通建议，不替代律师意见，不保证退款或就业结果。OCR文字、金额及条款解释需要人工复核。法规检索覆盖四部法规及司法解释中的46条选编，属于本机关键词检索，不是全国法规库，也不自动认定法律适用。

应用以单用户本机方式运行；原文件在内存中解析，调用模型前需用户确认，规则脱敏不能代替人工检查。历史记录仅在用户主动保存时写入本机，当前未加密，不适合直接作为公网多用户服务部署。

## 八、DEMO展示内容
三分钟以内演示以虚构求职辅导合同为材料，依次呈现：导入与正文核对、补充销售承诺、运行openJiuwen工作流、查看通俗报告并定位原文、查看承诺差异、展示退款情景试算与本机历史。重点展示用户如何从“看不懂约定”走向“知道需要确认什么”，并明确区分真实模型结果、确定性计算及待人工确认事项。
